## 2. Repository architecture inspected

`pom.xml` targets Java 21, JavaFX 21.0.9, Google GenAI SDK 1.80.0, Jackson databind 2.18.11 and JUnit Jupiter 5.11.4. Compiler, Surefire, exec and JavaFX Maven plugins are configured. `module-info.java` requires Java HTTP, JavaFX, Gemini and Jackson modules; it opens model/storage for Jackson and the application package for FXML. Build/startup checks found no module-access failure.

Production launch paths:

- GUI: `App` → persistent `EventPlanningFacade` → `EventPlanningController` → `GuiSession` → `Dashboard` and feature panels.
- CLI: `CLIApp` → persistent facade → shared controller → `EventPlanningCLI`.
- Backend: facade → `EventService`, `EventPlanningAgent`, task/schedule/budget services, `AdaptivePlanningService`, venue scoring and external tools.
- External AI: agent → `AIModel` → `GeminiAdapter` → `GeminiAPIClient` → official Google SDK.
- External listings: `VenueSearchTool` / `CateringSearchTool` → `PlacesAPIClient` → Places Text Search (New).
- Persistence: `PlanRepository` → `JsonPlanRepository`, explicit `PlanData` DTOs, `PlanDataMapper`, strict `StorageJson`; tests can use `InMemoryPlanRepository`.

The domain separates mutable `Event`/`PlanningTeam`/`User` aggregates from immutable records: ideas, concepts, blueprints, tasks, schedules/sessions/time slots, budget items/catering, venue options/evidence/comparisons, plan changes/scenarios, contingencies, communications and post-event data/reports. Stable IDs and record constructor checks are used extensively. The generated FXML starter controllers are retained but are not the Planit dashboard entry point.

## 4. Cross-cutting verification and gaps

### AI and provider integration

- Production facade construction uses the real Gemini adapter and real Places tools. Offline tests inject model/HTTP boundaries; they do not demonstrate live credentials, model availability, billing, quotas, current listings or provider accuracy.
- Gemini is lazy, has a 60-second SDK timeout, requests JSON MIME, rejects missing/blank text and emits sanitized configuration/transport errors. Agent JSON parsing rejects duplicate keys/trailing tokens and F01–F06 parsers validate schemas/source references with at most one malformed-output retry. No placeholder success response replaces unavailable Gemini.
- For F07–F10, `milestoneOutput` retries JSON syntax/object failures, but feature-specific required field validation occurs later in `AdaptivePlanningService`. A syntactically valid object missing required fields fails safely without the same retry. This difference is a reliability limitation, not silent success.
- Places uses `https://places.googleapis.com/v1/places:searchText`, a field mask, connect/request timeouts, source IDs and retrieval instants; it handles HTTP/network/parse failure without returning invented listings. Phone and website come from provider fields. Availability, capacity, rent and equipment remain unknown unless manual evidence supplies them. Google-reported wheelchair entrance is not full accessibility verification.
- A sourced contact is not independently verified contact information. The GUI correctly labels that distinction. The requirement for verified contacts is therefore only partially met; human confirmation is still needed. No email is inferred from Places.
- `PlanningStrategy.fromName` correctly maps budget/community/attendance to `BudgetPriorityStrategy`, `CommunityPriorityStrategy`, `AttendancePriorityStrategy`. Their different guidance is actually injected into blueprint and budget prompts. Strategies influence AI recommendations, not a deterministic global optimizer.

### State, approvals and GUI threading

- Both launchers use the same persistent facade factory/data-directory resolution. The repository takes an exclusive lock: GUI and CLI can share data sequentially, not run concurrent writable sessions. This is intentional protection, not live synchronization.
- Tasks, schedules and budgets keep proposals/edits in separate persisted draft maps. Approve validates before replacing approved records; discard retains the old approved plan. Communications store a per-record approval flag; edits clear it, and formal event changes return all communications to draft. No actual posting occurs.
- Revised F02 approval boundary: `selectedBlueprintId` is a pending choice; `approvedBlueprintId` independently identifies the execution alternative (null means none approved). Both references must belong to the event. Selection does not replace a previous approval. GUI confirmation and CLI `yes` explicitly approve the selection through the shared controller/facade. Changing approval retains tasks, schedules and drafts and records persistent review warnings visible in their panels/CLI views. It neither regenerates nor approves those execution plans.
- Exclusive F03/F04 context is verified by `BlueprintSelectionTest.bothExecutionPromptsContainOnlyApprovedAlternativeEvenWithDifferentPendingSelection`: each parsed request contains exactly one blueprint with the approved ID, agenda, checklist and resources; a conflicting pending alternative is absent. Both generation paths call `executionContext`, which iterates `Event.executionBlueprints()`. With alternatives but no approval, generation fails before AI with a clear select/approve message. With no blueprint alternatives at all, generation retains the explicitly labelled event-details/ideas/constraints-only fallback and an empty blueprint array. Existing saved work can still be viewed/edited before selecting a blueprint.
- Scope limit: this correction filters task/schedule execution context only. Budget/venue and adaptive-analysis contexts were not changed to enforce selected-blueprint exclusivity. Review warnings are advisory; current code does not prove that retained plans match the newly approved alternative, and the existing warning-clearance limitation remains.
- Formal F08 changes validate on a snapshot, require explicit UI/CLI confirmation, reject stale original facts, retain approved execution plans and notify registered services to record review warnings. Pending proposals survive restart.
- `Dashboard.background` uses a single worker and JavaFX completion handlers. AI, Places and persistent mutations are dispatched off the FX Application Thread. Startup storage loading occurs in `App.init`. Executed desktop tests verify background execution, duplicate submission rejection, navigation/event switching, persistence failure recovery and deferred resource cleanup. Local view construction/formatting stays on FX.
- `DisplayNames` maps event/member/speaker/concept/venue references to readable names and distinguishes duplicate names. Technical detail views intentionally retain raw records/IDs. Draft-only task IDs are absent from its approved-task lookup and may appear as unresolved references in some diagnostics; task rows themselves use titles.
- `DateTimeInput` commits DatePicker editor text, requires date/hour/minute, uses a 24-hour clock and preserves existing seconds/nanos. Executed tests confirm local values and reject incomplete/reversed intervals. There is no `ZoneId`, offset or DST policy in the event/time-slot/persistence model. The code avoids accidental host-zone conversion but cannot preserve a timezone it never stores. CLI help saying “event's local timezone” overstates that model.
- No dead feature button was found in inspected handler wiring. Desktop rendering tests cover every panel; November 14 interaction coverage explicitly includes F02 selection, confirmation/cancellation and approval switching, alongside the existing F07–F10, event creation and Places research checks. Complete F01 fusion, F02 live generation and F03–F06 execution approval workflows must still be demonstrated manually; panel rendering alone does not verify them.

## 6. Persistence and security

Original November 13 `PersistenceTest`: 15 tests passed. Those 15 tests passed again on November 14; the generated concept/blueprint/task/schedule/budget case now explicitly selects and approves its blueprint before execution and asserts restored approval. Existing cases include full nested graph/IDs/evidence/null-vs-zero round trip, canonical shared user/team identities, drafts and later approval after restart, generated plans saving automatically, communications/contingencies/reports, pending confirmed changes and Observer warnings, simulation byte preservation, deletion cleanup, malformed/unsupported/semantic corruption, save failure rollback, exclusive sessions/external modification and serialized facade mutations.

Newly executed November 14 `BlueprintSelectionPersistenceTest`: 4 tests passed. `PlanData.EventData` and `PlanDataMapper` capture/restore `selectedBlueprintId` and `approvedBlueprintId`; snapshots retain both references. The version-1 store accepts legacy events missing only these new optional properties by defaulting them to null in memory. Loading does not rewrite saved bytes; the next successful mutation writes the fields. Tests verify pending selection separate from existing approval across restarts, retained plans/warnings after switching, preserved IDs/approvals and monetary values, strict rejection of invalid references/missing original fields, and save-failure rollback. JSON tree parsing preserves BigDecimal precision/scale. No existing event is auto-approved merely because it has alternatives.

`JsonPlanRepository` creates a session lock, requires successful load before save, validates deserialized DTOs and restored graph, checks a digest against external changes, writes/flushed bytes to a same-directory temporary file and replaces the destination. Atomic move falls back to replacement where unsupported. Failed save triggers facade restoration of the prior captured state. Invalid/unreadable data aborts startup with an actionable error; it is not silently reset to an empty file. No claim is made of power-loss testing or automatic backup/repair.

Successful deletion removes the event, draft entries, pending changes and remaining team links from captured data; the restart test verifies it stays deleted. The default store is outside the repository (`LOCALAPPDATA/Planit` on Windows), with `planit.dataDir` / `PLANIT_DATA_DIR` overrides. Tests use temporary synthetic stores, not the user's store.

Tracked filename inspection found no tracked `.env`, `planit.json`, credential file or local configuration JSON; `.env.example` is tracked. Ignore rules cover `.env` variants (except example), `config.local.json`, Maven target, logs, temporary files and VS Code configuration. They do **not** expressly ignore `planit.json` or `planit.lock` if a user overrides storage into the repository. No real secrets were read or printed. This was not a Git-history secret scan or proof that no credential ever existed in history. API error logging uses allowlisted diagnostics rather than response/request bodies, headers or credentials. Persistence DTOs contain event data, not API configuration.

Local JSON contains personal/event information in plaintext under normal OS permissions. Encryption/access-control deployment requirements were not specified or tested. No external vulnerability/version currency assessment was performed; dependency versions above describe the repository, not a security certification.
